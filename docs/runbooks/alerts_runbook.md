# Alerts Runbook: SLA Violation Alerts

## Overview

This runbook documents the complex event processing (CEP) alerts generated by the Real-Time Order Delivery Event Platform. These alerts detect "Zalando-style" SLA violations in order processing.

## Alert Types

### 1. `paid_not_shipped_within_2h`

**Description**: Order was paid but not shipped within 2 hours.

**Severity Levels**:
- `WARNING`: 2-4 hours since payment
- `CRITICAL`: 4+ hours since payment

**Root Causes**:
1. **Warehouse Processing Delays**
   - High order volume overwhelming warehouse capacity
   - Staff shortages or shift gaps
   - Inventory management issues

2. **System Integration Issues**
   - Payment confirmation not reaching WMS (Warehouse Management System)
   - Order routing failures
   - API timeouts between systems

3. **Inventory Problems**
   - Items out of stock after payment
   - Inventory sync lag between channels
   - Pick failures due to mislocated items

**Troubleshooting Steps**:

```bash
# 1. Check alert volume by region and warehouse
docker exec -it local-trino-1 trino --execute "
  SELECT 
    region, 
    warehouse_id, 
    COUNT(*) as alert_count,
    AVG(time_since_last_event_hours) as avg_delay_hours
  FROM iceberg.lakehouse.gold_alerts
  WHERE alert_type = 'paid_not_shipped_within_2h'
    AND detected_at >= CURRENT_TIMESTAMP - INTERVAL '1' HOUR
  GROUP BY region, warehouse_id
  ORDER BY alert_count DESC
"

# 2. Check for patterns in affected orders
docker exec -it local-trino-1 trino --execute "
  SELECT 
    a.order_id,
    a.created_at as paid_at,
    a.time_since_last_event_hours,
    s.items_count,
    s.total_amount
  FROM iceberg.lakehouse.gold_alerts a
  LEFT JOIN iceberg.lakehouse.silver_order_state s 
    ON a.order_id = s.order_id
  WHERE a.alert_type = 'paid_not_shipped_within_2h'
    AND a.detected_at >= CURRENT_TIMESTAMP - INTERVAL '1' HOUR
  ORDER BY a.time_since_last_event_hours DESC
  LIMIT 20
"

# 3. Check Kafka topic for recent alerts
docker exec local-redpanda-1 rpk topic consume alerts.events --num 10 --offset end

# 4. Check Flink job health
docker exec local-flink-jobmanager-1 /opt/flink/bin/flink list

# 5. Check warehouse-specific order backlog
docker exec -it local-trino-1 trino --execute "
  SELECT 
    warehouse_id,
    COUNT(*) as pending_orders
  FROM iceberg.lakehouse.silver_order_state
  WHERE current_status = 'paid'
  GROUP BY warehouse_id
  ORDER BY pending_orders DESC
"
```

**Resolution Actions**:
1. Contact warehouse operations team for affected warehouses
2. Check WMS queue for blocked orders
3. Verify payment-to-fulfillment integration is healthy
4. If systemic, consider pausing new order intake

### 2. `shipped_not_delivered_within_5d`

**Description**: Order was shipped but not delivered within 5 days.

**Severity Levels**:
- `WARNING`: 5-7 days since shipping
- `CRITICAL`: 7+ days since shipping

**Root Causes**:
1. **Carrier Issues**
   - Carrier capacity problems
   - Weather delays
   - Customs/import delays (international)
   - Lost or misrouted packages

2. **Address Problems**
   - Incorrect delivery address
   - Address unreachable
   - Customer not available for delivery

3. **Regional Infrastructure**
   - Last-mile delivery failures
   - Remote area delivery challenges
   - Local logistics partner issues

**Troubleshooting Steps**:

```bash
# 1. Check alert distribution by region
docker exec -it local-trino-1 trino --execute "
  SELECT 
    region,
    COUNT(*) as alert_count,
    AVG(time_since_last_event_hours) as avg_delay_days
  FROM iceberg.lakehouse.gold_alerts
  WHERE alert_type = 'shipped_not_delivered_within_5d'
    AND detected_at >= CURRENT_TIMESTAMP - INTERVAL '24' HOUR
  GROUP BY region
  ORDER BY alert_count DESC
"

# 2. Identify problematic shipping patterns
docker exec -it local-trino-1 trino --execute "
  SELECT 
    warehouse_id as shipped_from,
    region as destination,
    COUNT(*) as delayed_orders,
    MAX(time_since_last_event_hours) as max_delay_days
  FROM iceberg.lakehouse.gold_alerts
  WHERE alert_type = 'shipped_not_delivered_within_5d'
    AND detected_at >= CURRENT_TIMESTAMP - INTERVAL '7' DAY
  GROUP BY warehouse_id, region
  ORDER BY delayed_orders DESC
  LIMIT 10
"

# 3. Check for carrier-specific issues (if tracking data available)
docker exec -it local-trino-1 trino --execute "
  SELECT 
    order_id,
    created_at as shipped_at,
    time_since_last_event_hours / 24.0 as days_since_shipped
  FROM iceberg.lakehouse.gold_alerts
  WHERE alert_type = 'shipped_not_delivered_within_5d'
    AND severity = 'CRITICAL'
  ORDER BY time_since_last_event_hours DESC
  LIMIT 20
"

# 4. Compare against normal delivery times
docker exec -it local-trino-1 trino --execute "
  SELECT 
    region,
    AVG(delivery_time_minutes) / 60.0 as avg_delivery_hours,
    COUNT(*) as total_deliveries,
    SUM(CASE WHEN on_time THEN 1 ELSE 0 END) as on_time_count
  FROM iceberg.lakehouse.silver_order_state
  WHERE is_delivered = TRUE
  GROUP BY region
"
```

**Resolution Actions**:
1. Contact carrier for affected routes
2. Proactively notify customers about delays
3. Consider alternative shipping methods for critical orders
4. Escalate to regional logistics team

## Alert Spike Investigation

When alerts spike unexpectedly, follow this process:

### Step 1: Assess the Scope

```bash
# Get alert rate over time
docker exec -it local-trino-1 trino --execute "
  SELECT 
    alert_type,
    DATE_TRUNC('hour', detected_at) as hour,
    COUNT(*) as alert_count
  FROM iceberg.lakehouse.gold_alerts
  WHERE detected_at >= CURRENT_TIMESTAMP - INTERVAL '24' HOUR
  GROUP BY alert_type, DATE_TRUNC('hour', detected_at)
  ORDER BY hour DESC
"
```

### Step 2: Check System Health

```bash
# Flink jobs status
docker exec local-flink-jobmanager-1 /opt/flink/bin/flink list

# Kafka topic lag
docker exec local-redpanda-1 rpk group list
docker exec local-redpanda-1 rpk group describe alert-detector

# Check for Flink exceptions
docker logs local-flink-taskmanager-1 --tail 100 | grep -i error
```

### Step 3: Identify Root Cause

| Symptom | Likely Cause | Action |
|---------|--------------|--------|
| All regions affected equally | System-wide issue (integration, data) | Check integrations |
| One region spike | Regional logistics/warehouse issue | Contact regional ops |
| One warehouse spike | Warehouse-specific problem | Contact warehouse |
| Gradual increase | Capacity/backlog building | Scale resources |
| Sudden spike | Incident or data issue | Check for outages |

### Step 4: Document and Communicate

1. Create incident ticket with:
   - Alert type and volume
   - Affected regions/warehouses
   - Root cause (if identified)
   - Customer impact estimate

2. Notify stakeholders via appropriate channels

## Prometheus Alert Thresholds

These alerts fire based on the rate of CEP alerts:

| Alert | Threshold | Duration | Severity |
|-------|-----------|----------|----------|
| HighPaidNotShippedAlertRate | >10/sec | 5m | Warning |
| CriticalPaidNotShippedAlertRate | >50/sec | 2m | Critical |
| HighShippedNotDeliveredAlertRate | >5/sec | 10m | Warning |
| CriticalShippedNotDeliveredAlertRate | >25/sec | 5m | Critical |

### Adjusting Thresholds

Thresholds should be tuned based on:
- Normal baseline alert rate
- Business SLA requirements
- Seasonality (holidays, sales events)

Edit `local/prometheus_alert_rules.yml` to adjust.

## Quick Reference Queries

```sql
-- Active alerts summary
SELECT alert_type, severity, COUNT(*) as count
FROM iceberg.lakehouse.gold_alerts
WHERE detected_at >= CURRENT_TIMESTAMP - INTERVAL '1' HOUR
GROUP BY alert_type, severity;

-- Top problematic warehouses
SELECT warehouse_id, COUNT(*) as alerts
FROM iceberg.lakehouse.gold_alerts
WHERE detected_at >= CURRENT_TIMESTAMP - INTERVAL '24' HOUR
GROUP BY warehouse_id
ORDER BY alerts DESC LIMIT 5;

-- Alert trend (hourly)
SELECT 
  DATE_TRUNC('hour', detected_at) as hour,
  alert_type,
  COUNT(*) as alerts
FROM iceberg.lakehouse.gold_alerts
WHERE detected_at >= CURRENT_TIMESTAMP - INTERVAL '7' DAY
GROUP BY 1, 2
ORDER BY 1 DESC;
```
